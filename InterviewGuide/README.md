# InterviewGuide

面接官向けの進め方と評価基準。

このリポジトリは公開されており、想定解答（各問題の `ANSWER.md`）も受験者が事前に読める前提で運用する。
**正解を知っているかではなく、対話の中で考え方を説明できるか**を評価する。

## 時間配分（60分枠の例）

| 時間 | 内容 |
|---|---|
| 5分 | アイスブレイク、進め方の説明 |
| 15〜20分 | CodeReview 1問 |
| 25〜30分 | Algorithm 1問 |
| 5分 | 逆質問 |

45分枠なら CodeReview か Algorithm のどちらか1問に絞る。

## 出題前の準備

* 受験者のレベルに合わせて難易度を選ぶ（★ = 新卒・ジュニア、★★ = 実務経験者、★★★ = シニア）
* 出題するファイルと `ANSWER.md` に目を通し、深掘り質問を1〜2個決めておく
* 使用言語は受験者に選んでもらう。出題コードは JavaScript だが、修正や実装は得意な言語で書いてよい

## 出題の進め方

### CodeReview

1. **コードだけ**を共有する（ディレクトリ名や README はテーマのヒントになるので見せない）
2. Q1〜Q4 を順に聞く。Q2 で詰まったら、具体的な入力を一緒に追う（「`[5, 0, -3]` を渡すとどうなりますか？」）
3. Q3 の修正は、口頭で方針を述べてもらうだけでもよい
4. Q4 は正解のない設計の議論。受験者の提案に「それをすると何が嬉しいか / 何が困るか」を聞き返す

### Algorithm

1. 問題文と入出力例を共有し、まず制約や前提について質問がないか聞く
2. 最初は素朴な解でよいと伝える。計算量を言ってもらってから改善を促す
3. 各問題の段階ヒントは、2〜3分手が止まってから1つずつ出す
4. 書き終えたら、エッジケース（空、要素1つ、重複、負数など）を受験者自身にテストしてもらう

### 運用メモ

* 沈黙が続いたら「今どこまで考えていますか？」と状況を言語化してもらう
* 間違った方向に進んでいても、すぐには止めない。自分で気づけるかも評価対象
* 想定解答と違う解でも、正しく説明できていれば加点する
* 事前に `ANSWER.md` を読んできた様子があれば、深掘り質問で理解の深さを確かめる

## 評価基準

各項目を 1〜4 点で付ける。

| 点 | 目安 |
|---|---|
| 1 | ヒントがあっても到達できない |
| 2 | ヒントがあれば到達できる |
| 3 | 自力で到達できる |
| 4 | 自力で到達し、根拠（再現する入力・計算量・トレードオフ）まで示せる |

### CodeReview

| 項目 | 対応する設問 | 見るポイント |
|---|---|---|
| 読解力 | Q1 | 挙動を正確に言語化できるか。具体例で説明できるか |
| バグ発見 | Q2 | 境界値・型・副作用に気づけるか。バグを再現する入力を挙げられるか |
| 修正力 | Q3 | 最小限で正しい修正か。正しく動いている部分を壊していないか |
| 設計力 | Q4 | 引数化・責務分離・テストのしやすさなどを提案できるか |

### Algorithm

| 項目 | 見るポイント |
|---|---|
| 問題理解 | 制約や曖昧な点を自分から確認できるか |
| 解法 | 素朴解から改善解へ進めるか |
| 計算量 | 時間計算量と空間計算量を正しく見積もれるか |
| 実装 | 動くコードを書けるか。読みやすいか |
| 検証 | エッジケースを自分で挙げてテストできるか |

### 共通

| 項目 | 見るポイント |
|---|---|
| コミュニケーション | 考えを口に出せるか。前提を確認できるか。ヒントを活かせるか |
